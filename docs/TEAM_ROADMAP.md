# Lulu 三人分工与技术 Roadmap

更新日期：2026-10-08。项目仓库：[kirk-ai2026/Global-e-commerce](https://github.com/kirk-ai2026/Global-e-commerce)。

三个人围绕商品、用户体验、交易履约三个领域并行建设。A（你）负责商品数据、内容、统一定价与可售规则及上货；B 负责网站、WhatsApp 和 Shopping Bestie 的交互与对话设计；C 负责订单、采购履约、实际费用回传以及公共运行基础设施。会话与 Agent 工具编排由 B／C 共同完成：B 主责场景、上下文和工具使用策略，C 主责会话持久化、执行调度和可靠性。各子模块保留明确写入方，团队之间通过版本化接口和事件协作。

第一期仍是现有天猫国际东亚／东南亚品牌货盘的简中内部成品，覆盖食品、保健品、美妆个护和母婴。加拿大、CAD 为首发市场与币种；实际店铺发布和交易按后续里程碑启用。实时搜索、大陆／台湾货盘扩展和英语生成属于本 Roadmap 的明确交付：分别安排在 R4 的两条工作流和 R6，不纳入第一期交付。

## 一 三个人的责任边界

| 主责 | 核心结果 | 维护的业务数据 | 边界 |
|---|---|---|---|
| A 你 | 有证据、统一定价、可审阅、能发布和更新的商品 | 来源观察、品牌与类目、SPU／SKU、媒体、内容、预测重量、定价公式、CAD 报价、市场资格、可售配额、发布版本、商品分析 | 统一维护商品事实、商业规则和商品相关 Shopify 写入；接收 C 的采购／物流实测反馈 |
| B | 用户能从网站和 WhatsApp 发现、理解并购买商品 | 客户身份映射、授权、偏好、对话／触达策略、行为归因 | 主责网站、渠道、Prompt、上下文策略和工具 schema；与 C 联调会话及执行后端，不改商品事实和订单状态 |
| C | 订单可采购、物流售后可追溯、Agent 调用可靠执行 | 订单、预留／释放、采购、包裹、实际重量／费用、物流、退款及对账；会话运行态、消息历史和工具执行回执 | 使用 A 的有效报价和可售规则履约；与 B 共建会话及编排，维护持久化、调度、权限校验、重试与恢复 |

### 统一定价口径

沿用无界的工程方法，将定价作为商品生产链路的一部分：采购价、规格及预测重量 → 预计运费 → 定价公式、汇率与服务费 → CAD 报价 → 市场资格及可售配额 → 发布。计费重量取值、运价、汇率、服务费和舍入方式由 A 版本化管理，加拿大参数显式配置。

重量预测保留依据与预测区间；金额由确定性程序计算。C 回传实际采购成本、实测／计费重量、物流费用及路线能力，A 用这些数据校准预测与定价参数。新参数作用于后续报价，不改写已锁定订单的成交金额。商品、网站和 WhatsApp 共用 A 的同一份有效报价。

### Shopify 的写入边界

- A 维护商品发布模块，统一计算并写入商品内容、规格、媒体、价格／可售配额，保存远端 ID、版本和回执。
- B 维护主题、页面、购物车与结账体验；商品修改从 A 的运营入口进入，不另做商品写入链路。
- C 维护订单、履约、退款等 Shopify 操作；采购成本、订单预留／释放、实际消耗和履约能力变化通过幂等事件回传 A，由 A 更新报价及对外可售余量；订单减少库存等平台行为通过事件对账。
- 商品同步、单独改价、库存变化分别执行，避免完整商品载荷覆盖新报价或误删规格。

按依赖和验收排期，不在人员、预算和外部输入尚未锁定时承诺日历日期。每一阶段末进行一次三人联调，业务开卖使用明确的首批商品范围。

### 可以提前并行的工作

- B 在 R0—R1 即可用 A 的现有成品和明确标记的 mock 报价搭建网站，不等全货盘完成。
- A 同期配置预测重量、定价公式、市场资格和可售规则；C 提供路线／运价依据并搭建订单与履约模拟，不等商品工厂放量。
- B／C 可在 R0—R1 提前共同开发会话和工具编排；正式 Agent 推荐使用 A 的可售目录及有效报价，订单问答接 C。
- R2 不等待实时搜索即可完成网站首单；R4 复用上货链路处理长尾。
- R4a 实时搜索与 R4b 大陆／台湾货盘是两个独立工作流，可并行：搜索接口不要求先补完整货盘，批量扩货不要求搜索 Agent 先上线。
- R5 主动关系和 R6 英语可在核心对话／交易契约稳定后分别开发；A 负责供给／语言内容，B／C 协作体验和执行，分别验收启用。
- R6 先在加拿大启用英语，多市场销售独立验证；不以美国／欧洲上线为英语生成的前置条件。Rakuten、Coupang 等平台保留适配方向，另行立项。

全货盘补证持续运行。首批交易验收不要求 8,152 个来源商品全部变成可售商品；运营目标仍是逐步完成目标货盘，并明确每项暂缓或排除的原因。

## 四 先冻结八份交接契约

| 契约 | 主责 | 提供给谁 | 最小交付内容 |
|---|---|---|---|
| Product 成品商品 | A | B／C | 稳定商品／SKU 引用、简中内容、媒体、成品状态与事实版本；内部成本与消费者展示分开 |
| ProcurementFacts 采购事实 | A | C | 来源商品／SKU、采购链接、CNY 观察价、库存观察、规格／重量依据、时间和证据版本 |
| CommercialQuote 商业报价 | A | B／C | CAD 商品价、运费／税费展示口径、预测重量及公式／汇率版本、报价性质／有效期、可售／配送资格、配额及规则版本 |
| Publication 发布结果 | A | B／C | Shopify Product／Variant ID、购买链接、发布范围、Manifest／报价版本和读回状态 |
| CustomerContext 客户与授权 | B | C；必要的偏好条件给 A | 验证后的客户引用、渠道身份绑定、授权／退订、偏好；按需传递，不共享完整会话和个人资料 |
| OrderStatus 订单与履约 | C | B；去个人化经营信号给 A | 授权可查的订单引用、采购／物流／售后阶段、时间、异常原因及可展示信息 |
| FulfillmentActuals 实际履约反馈 | C | A | 商品／SKU、订单及包裹构成、实际采购成本、实测／计费重量、物流费用、路线和数据时间，供预测与定价校准 |
| ConversationExecution 会话与工具执行 | B 主责语义／工具协议，C 主责执行／存储 | B／C；领域工具分别接 A／C | 客户／会话引用、消息生产者／来源、原始与规范化内容、工具参数／结果、运行状态、幂等键、权限范围和调用／送达回执 |

商品、报价、订单、授权与消息事件均带唯一事件 ID、实体引用、版本、时间和关联 ID，接收方支持幂等和重放。接口变更由主责方先更新契约与样例，再进行实现。

责任边界固定如下：

- A 分开维护来源库存观察、可售配额规则及对外剩余量；C 维护订单预留／释放和实际履约数据，用幂等事件反馈 A。
- C 锁定订单时使用的商品、SKU、报价与采购版本，商品更新不重写历史订单。
- 多 SKU 合包的实测反馈保留包裹构成，不能把包裹总重直接作为每个 SKU 的实物重量。
- B 展示 A 的有效报价和可售状态、C 的订单与物流事实，不让语言模型计算金额或承诺物流状态。
- B 定义系统、Agent、人工及外部消息的语义和对话策略；C 维护消息历史、顺序及回执。B／C 共同保证系统可控消息的实际内容、回执和 Agent 上下文一致；发送成功不自动等同历史记录完成。
- B 维护 Prompt、上下文选择和工具 schema；C 执行工具参数校验、权限、并发顺序、超时及恢复。商品领域工具调用 A，订单／履约工具调用 C，不在编排层复制公式或改写事实。
- 各人维护自己领域的数据；跨领域调用服务或消费事件，不直接写对方业务表。

## 五 协作与跨部门输入

先维持一个仓库与模块化结构。按商品、体验、交易履约及会话执行拆分路由、Repository 和迁移文件，避免三个人同时改大型共享 `api.py`／`storage.py`。商品 ID／事实契约由 A 主责，公共运行时与部署规范由 C 主责；用户和渠道契约由 B 主责，会话／工具协议由 B／C 联合维护。会话及执行记录由 C 的存储接口写入，B 通过接口读取或提交事件。

每个人使用功能分支和 PR，合并前跑模块测试与共享契约测试；不在个人机器自动部署生产。C 维护整合环境与发布记录，模块负责人确认自己的验收结果。每阶段联合回归至少包括重复任务、失败重试、来源变化、SKU 图价绑定、重复 Webhook、用户授权和异常订单。

| 外部输入 | 协调主责 | 落地方式 |
|---|---|---|
| 首批品牌／品类、描述标准、图片使用范围与素材权利 | A | 货盘清单、QA 规则、审核记录 |
| 定价公式、预测重量、服务费、汇率、税费／运费及可售配额 | A | 财务／合规确认的版本化配置；C 提供路线能力、运价依据和实测数据，未确定时保持不启用 |
| 加拿大商品销售资格和渠道商品限制 | A 协调销售资格，B 协调消息／广告渠道限制 | 各自独立资格规则，不把网站可卖直接当作 WhatsApp 可推荐 |
| 退款执行和资金对账 | C | 按确认的售后／财务规则执行，保留订单成交报价和实际费用 |
| 采购、集货、质检、运输、配送范围、时效与售后 | C | 流程、能力配置、回执与异常处理 |
| 店铺、支付、主题、WhatsApp／Meta 账户和渠道模板 | B | 测试与生产连接、前台配置、消息授权／模板 |
| 预算与成本上限 | 各模块主责申报，C 汇总平台用量 | A 管采集／内容／媒体成本，B 管 Agent／消息成本，C 管基础设施／履约接口成本 |

优先级为：当前内部成品链路补齐 → 正式报价及发布 → 网站首单履约 → B／C 共建 WhatsApp 购物助手 → 实时搜索与大陆／台湾货盘两线扩展 → 主动复购／加拿大英语。后三项均有明确模块、交付和验收，按依赖启用；每人聚焦当前阶段的主要结果。

## 六 当前起点与第一批任务

截至 2026-10-08，本地底座有 42 项通过的测试；范围内 8,152 个来源商品中，6 个形成完整内部成品，8,145 个待补证，1 个明确停售。数据处理完成不等于全部商品已完成上货。详细口径见 [首次验收记录](RUN_RESULTS.md)。

- **A 本阶段：**整理 30 个首批目标商品的缺口，优先接通指定 ID 补详情和媒体审核／修复；建立预测重量、统一定价公式及 CAD 报价／可售 DTO，向 B／C 提供样例与测试版本。
- **B 本阶段：**建立中文主题与集合／详情模板，使用现有成品联调；准备 WhatsApp 开发接入，与 C 确定会话事件、上下文与工具协议，不依赖搜索 Actor。
