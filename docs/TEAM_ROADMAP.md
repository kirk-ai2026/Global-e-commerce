# Lulu 三人分工与技术 Roadmap

更新日期：2026-10-08。项目仓库：[kirk-ai2026/Global-e-commerce](https://github.com/kirk-ai2026/Global-e-commerce)。

三个人围绕商品、用户体验、交易履约三个领域并行建设。A（你）负责商品数据、内容及上货；B 负责网站、WhatsApp 和 Shopping Bestie；C 负责定价、订单、采购履约以及公共运行基础设施。每份业务数据只有一个主责写入方，团队之间通过版本化接口和事件协作。

第一期仍是现有天猫国际东亚／东南亚品牌货盘的简中内部成品，覆盖食品、保健品、美妆个护和母婴。加拿大、CAD 为首发市场与币种；实际店铺发布和交易按后续里程碑启用。实时搜索、扩大陆／台湾货盘和英语生成继续后置。

## 一 三个人的责任边界

| 主责 | 核心结果 | 维护的业务数据 | 边界 |
|---|---|---|---|
| A 你 | 有证据、可审阅、能发布和更新的商品 | 来源观察、品牌与类目、SPU／SKU、媒体、内容、发布版本、商品分析 | 商品事实与商品相关 Shopify 写入集中维护；正式售价和可售配额由 C 提供 |
| B | 用户能从网站和 WhatsApp 发现、理解并购买商品 | 客户身份映射、授权、偏好、会话、触达记录、行为归因 | 维护体验、渠道和必要的轻后端；通过 A／C 的工具读商品、报价和订单，不改事实和订单状态 |
| C | 报价可执行、订单可采购、物流售后可追溯 | 商业报价、市场资格、库存配额／预留、订单、采购、包裹、物流、退款及对账 | 维护交易与履约事实；收集财务、合规和物流负责人确认的规则，不由模型生成这些规则 |

公共运行时、CI/CD、环境、认证、Secret、备份及告警由 C 主责；A、B 各自承担模块部署配置、测试、监控与故障修复。公共基础设施不是把其他两个人的模块排错也交给 C。

默认 B 除前端外，能承担 WhatsApp Webhook、会话和 Agent 工具编排等必要轻后端；不需要承担商品生产或采购履约核心。

### Shopify 的写入边界

- A 维护商品发布模块，统一写商品内容、规格、媒体以及 C 提供的价格／库存配额，保存远端 ID、版本和回执。
- B 维护主题、页面、购物车与结账体验；商品修改从 A 的运营入口进入，不另做商品写入链路。
- C 维护订单、履约、退款等 Shopify 操作；商品价格／库存调整通过版本化请求交给 A 应用，订单减少库存等平台行为通过事件对账。
- 商品同步、单独改价、库存变化分别执行，避免完整商品载荷覆盖新报价或误删规格。

## 三 三人并行 Roadmap

按依赖和验收排期，不在人员、预算和外部输入尚未锁定时承诺日历日期。每一阶段末进行一次三人联调，业务开卖使用明确的首批商品范围。

| 阶段 | A 你 | B | C | 联合验收 |
|---|---|---|---|---|
| R0 接口与工程基线 | 冻结商品 ID、状态、DTO；提供现有 6 个成品和边界测试数据 | 准备开发店／主题与 WhatsApp 测试接入；确定展示字段、客户引用和会话契约 | 配置公共开发／测试环境、CI、Secret 与权限；提出报价／订单 DTO | 三个人都能独立启动或使用 mock 联调；不能把历史 CNY 采购价当 CAD 售价 |
| R1 各自完成第一条链路 | 指定 ID 补证、媒体生产／QA、简中成品、补证与审核；先产出稳定真实批次 | 用真实成品／测试商业数据完成网站页面；打通 WhatsApp 测试收发、会话与人工接管 | 实现 CAD 报价和可售配置；建订单／采购／物流状态与内部操作入口 | 商品测试样本覆盖四品类与缺项；至少 30 个合格内部成品；开发环境体验与履约模拟各自可演示 |
| R2 上架与首单闭环 | 接 C 的报价／资格，创建开发店 Draft、读回，再准备受控发布与商品同步 | 完成中文网站、CAD／配送展示、购物车与结账；验证页面和商品链接 | 接订单 Webhook，完成采购记录、集货／运单、物流状态、异常和退款对账 | 一笔测试订单全链路可追溯；重复事件不重复采购；发布数据与网站一致。业务确认后开展受控真实订单 |
| R3 WhatsApp 购物助手 | 提供已发布目录检索、商品解释资料、购买链接和商品变化事件 | 上线固定货架 Shopping Bestie、授权／身份绑定、订单问答及转人工 | 提供报价、配送、订单状态和售后工具；持续验证采购与物流规则 | WhatsApp 推荐 → 网站结账 → 订单状态问答闭环；不编造价格／库存／时效；系统消息进入会话历史 |
| R4 按需搜索与货盘扩展 | 评测 Apify 搜索 Actor，优化 30 秒期限，支持选中后商品化；扩大陆／台湾货盘 | 对话查询、条件追问、等待／失败表达、选中后商品化进度及购买链接 | 验证新增商品／来源采购路线、资格、报价、配额和履约时效 | 先搜索、再补证和商品化、最后购买；列表价不直接成为结账价；技术失败不等于无货 |
| R5 主动关系与英语扩展 | 主题素材、可追溯 Social Proof、商品变化；增加英语内容／QA | 个性化货架、补货／新品推荐、触达频率与退订、归因；英语网站／Agent | 输出补货／履约事件、复购对账；逐步增加市场配置 | 只在授权及渠道资格范围内触达；退订有效；新语言不重建商品或 SKU |

### 可以提前并行的工作

- B 在 R0—R1 即可用 A 的现有成品和明确标记的 mock 报价搭建网站，不等全货盘完成。
- C 同期收集费用、销售资格和物流路线，搭建报价与订单模拟，不等商品工厂放量。
- B 可提前开发 WhatsApp 网关；正式 Agent 推荐需等 A 的可售目录与 C 的有效报价。
- R2 不等待实时搜索即可完成网站首单；R4 复用上货链路处理长尾。
- R4 的供给扩展与 R5 的画像／主动关系可分别由 A 与 B 推进，C 按新增商业与履约需求接入。
- 英语及其他市场在加拿大简中闭环稳定后启用。Rakuten、Coupang 等平台保留适配方向，另行立项。

全货盘补证持续运行。首批交易验收不要求 8,152 个来源商品全部变成可售商品；运营目标仍是逐步完成目标货盘，并明确每项暂缓或排除的原因。

## 四 先冻结六份交接契约

| 契约 | 主责 | 提供给谁 | 最小交付内容 |
|---|---|---|---|
| Product 成品商品 | A | B／C | 稳定商品／SKU 引用、简中内容、媒体、成品状态与事实版本；内部成本与消费者展示分开 |
| ProcurementFacts 采购事实 | A | C | 来源商品／SKU、采购链接、CNY 观察价、库存观察、规格／重量依据、时间和证据版本 |
| CommercialQuote 商业报价 | C | A／B | CAD 商品价、运费／税费展示口径、报价性质／有效期、可售／配送资格、配额及规则版本 |
| Publication 发布结果 | A | B／C | Shopify Product／Variant ID、购买链接、发布范围、Manifest／报价版本和读回状态 |
| CustomerContext 客户与授权 | B | C；必要的偏好条件给 A | 验证后的客户引用、渠道身份绑定、授权／退订、偏好；按需传递，不共享完整会话和个人资料 |
| OrderStatus 订单与履约 | C | B；去个人化经营信号给 A | 授权可查的订单引用、采购／物流／售后阶段、时间、异常原因及可展示信息 |

商品、报价、订单、授权与消息事件均带唯一事件 ID、实体引用、版本、时间和关联 ID，接收方支持幂等和重放。接口变更由主责方先更新契约与样例，再进行实现。

责任边界固定如下：

- A 的来源库存是观察事实，C 的可售配额是商业状态，两者不互相覆盖。
- C 锁定订单时使用的商品、SKU、报价与采购版本，商品更新不重写历史订单。
- B 展示 C 的有效报价和订单事实，不让语言模型计算金额或承诺物流状态。
- B 负责对系统、Agent、人工及外部消息分类；系统可控消息的实际内容、回执和 Agent 历史一致。渠道发送成功不自动等同历史记录完成。
- 各人维护自己领域的数据；跨领域调用服务或消费事件，不直接写对方业务表。

## 五 协作与跨部门输入

先维持一个仓库与模块化结构。按商品、体验、交易履约拆分路由、Repository 和迁移文件，避免三个人同时改大型共享 `api.py`／`storage.py`。商品 ID／事实契约由 A 主责，公共运行时与部署规范由 C 主责；B 主责用户和渠道契约。

每个人使用功能分支和 PR，合并前跑模块测试与共享契约测试；不在个人机器自动部署生产。C 维护整合环境与发布记录，模块负责人确认自己的验收结果。每阶段联合回归至少包括重复任务、失败重试、来源变化、SKU 图价绑定、重复 Webhook、用户授权和异常订单。

| 外部输入 | 协调主责 | 落地方式 |
|---|---|---|
| 首批品牌／品类、描述标准、图片使用范围与素材权利 | A | 货盘清单、QA 规则、审核记录 |
| 定价、服务费、汇率、税费／运费、退款规则 | C | 财务确认的版本化配置，未确定时保持不启用 |
| 加拿大商品销售资格和渠道商品限制 | C 协调销售资格，B 协调消息／广告渠道限制 | 各自独立资格规则，不把网站可卖直接当作 WhatsApp 可推荐 |
| 采购、集货、质检、运输、配送范围、时效与售后 | C | 流程、能力配置、回执与异常处理 |
| 店铺、支付、主题、WhatsApp／Meta 账户和渠道模板 | B | 测试与生产连接、前台配置、消息授权／模板 |
| 预算与成本上限 | 各模块主责申报，C 汇总平台用量 | A 管采集／内容／媒体成本，B 管 Agent／消息成本，C 管基础设施／履约接口成本 |

优先级为：当前内部成品链路补齐 → 正式报价及发布 → 网站首单履约 → WhatsApp 购物助手 → 实时搜索／扩货盘 → 主动复购与英语。每人同时聚焦自己当前阶段的一个主要结果，避免把三个人排成一个串行流水线。

## 六 当前起点与第一批任务

截至 2026-10-08，本地底座有 42 项通过的测试；范围内 8,152 个来源商品中，6 个形成完整内部成品，8,145 个待补证，1 个明确停售。数据处理完成不等于全部商品已完成上货。详细口径见 [首次验收记录](RUN_RESULTS.md)。

- **A 本阶段：**整理 30 个首批目标商品的缺口，优先接通指定 ID 补详情和媒体审核／修复；向 B／C 提供稳定商品 DTO、样例与测试版本。
- **B 本阶段：**建立中文主题与集合／详情模板，使用现有成品联调；同时准备 WhatsApp 开发接入和会话记录，不依赖搜索 Actor。
- **C 本阶段：**建立 CAD 报价／可售 DTO、采购履约流程与订单状态模拟；配置公共测试环境和 CI，收集财务／合规／物流输入。

第一批三人联合交付物是：一套稳定契约、一个可展示的网站原型、一组真实合格成品、一个可执行报价／履约模拟，以及端到端测试记录。
